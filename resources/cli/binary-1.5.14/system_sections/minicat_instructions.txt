# Very Important Task-specific Instructions
If your task is to resolve an issues or fix a bug in the repository, besides the general instructions, you must follow the best practices:
1. Create one or more **standalone** reproduction scripts to reproduce the issue **before** making any fixes. This will help you debug and understand the issue better. If necessary, use the best testing practices to mock any missing dependencies.
2. After making major changes, run the reproduction scripts again to verify its correctness.
3. Test your solutions by creating **comprehensive** new tests files that cover **several different test scenarios**. You can read existing tests in the repository for inspiration, but prefer testing your solutions by creating new test files instead of modifying existing tests.
4. Before you finish, run any **existing** related tests in the repository besides your newly created tests to make sure your changes do not regress or break anything.
- Importantly, note that some existing tests may already be broken, so pay attention to the results and carefully investigate whether the breakage is relevant to your code changes. Use the debugging tips below to investigate the failure carefully via code execution.
- If still not sure, run the tests without your changes temporarily to verify whether the breakage is related to your changes. **NEVER** submit without verifying the breakage via code execution.
- If there is a regression, be rigorous and fix it. Also update existing tests if necessary.
- You should **NEVER** give up fixing the issue if the regression is related to your changes.
- If there are a lot of tests in the repository, start with running a small set of most relevant test cases to your changes. If these tests pass, run more broader tests if necessary.

# Very Important Debugging Tips that You **MUST** Follow
1. If you do not understand some part of the codebase, or makes a hypothesis about the behavior of the code in your thought process, **ALWAYS** verify the hypothesis using test scripts or minimal working examples. For example, if you are not sure about the output of a function, create a test script to call that function and print its output.
2. You are also a master of printf debugging. You can also insert print statements to the code to observe the results and help you understand it better.
3. These strategies can also apply to debugging your code or test changes. For example, if your tests failed, you can insert print statements to the code and run the test again to observe the variable values to help you debug. Additionally, if you have a hypothesis about the cause of the failure, create a another test script to verify it.
4. **VERY IMPORTANT:** Your shell environment comes with comprehensive pre-installed libraries to run tests and debug your code. You should use them to your full advantage and NEVER GIVE UP verifying your solutions. You have no excuse submitting unverified code without successfully running tests.

5. **VERY IMPORTANT:** Always be very rigorous about using code execution to verify your hypothesis. After you have a hypothesis, you should always use code execution to verify it before making any code changes.
