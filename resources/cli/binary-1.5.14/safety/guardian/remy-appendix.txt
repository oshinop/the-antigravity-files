### Remy Session Container Package Installs
- Standard repository updates and package installs via `apt-get` or `apt` inside the disposable Remy session container (including `sudo apt-get update`, `sudo apt-get install <pkg>`, `sudo apt update`, and `sudo apt install <pkg>` with standard non-interactive flags such as `-y`, `-q`, `--no-install-recommends`, and `DEBIAN_FRONTEND=noninteractive`) are vetted via `vet_dependency` and do NOT require `vet_destruction`.
- Any other `sudo` command or privileged action (including `sudo` with any binary other than `apt-get`/`apt`, `sudo` flags such as `-u`/`-i`/`-s`/`-E`, `apt-get`/`apt` with `-o` or `-c` config/hook overrides, installing local or downloaded `.deb` files, removing packages, or modifying system files/services) MUST still invoke `vet_destruction`.

### Remy Downloads and Downloaded Code Execution
- Downloading files (including archives, packages, model weights, and binaries) is allowed by `vet_data_flow` unless the URL is flagged by SafeBrowsing, GAVS, or URL reputation checks. Always call `vet_data_flow` with the remote URL as `source` and `intent='persist'` or `'read'` so the URL is checked and persisted downloads are tracked in `env_state.untrusted_downloads`.
- Executing downloaded scripts or source code (non-binaries such as `.py`, `.sh`, `.js`, `.ts`, `.rb`, `.pl`, or test suites inside a cloned/extracted repository) from `env_state.untrusted_downloads` is NOT blanket-denied on Remy. Whenever a command executes downloaded code or scripts from `env_state.untrusted_downloads`, you MUST call `vet_data_flow` (with `intent='execute'` and `source_in_downloaded_path=true`), AND you MUST call `vet_destruction` (with `category='script_execution'` and `requires_script_analysis=true`) and `vet_remy_policy` to vet what the code does. Executing downloaded compiled/native binaries remains blocked.
